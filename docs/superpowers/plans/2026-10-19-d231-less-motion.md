> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One Appearance switch, Less motion, that makes SKIPTI behave on both phones exactly as it does under the phone's own Reduce Motion, on by itself on a low-memory phone until the person sets it.

**Architecture:** A pure `MotionSetting` (parse, low-RAM rule, the one OR) and `MotionCopy` on each shell, in the motion files (`ThemeMotion.swift` / `ThemeMotion.kt`). Each shell gets ONE door: iOS a `\.motionReduced` environment value set by `AppearanceApplier` at the root (every view that read the phone's Reduce Motion reads it instead; the one imperative read goes through `MotionSetting.reducedNow()`); Android `rememberMotionState()`, whose `reduce` becomes the phone's input OR `Appearance.lessMotion` through `MotionState.of`. A source guard on each shell holds the door. Then a `HapticsRow` twin, `MotionRow`, with Lucide `sparkles`.

**Tech Stack:** SwiftUI (iOS 17+, Swift 5 mode, XCTest hosted in the app), Jetpack Compose (minSdk 26, JUnit 4 JVM tests, no Robolectric), Python 3 stdlib for the runners. No new dependency.

**Spec:** `.drafts/d231/spec.md` (binding; decisions 68 to 72). Branch: `d231-less-motion`, cut by the controller. Implementers never switch branches.

## Deviations from the spec (proposed; the controller confirms or overturns)

1. **Android storage key is `lessMotion`, not `appearance.lessMotion`.** The code's own convention: Android keeps appearance choices unprefixed in their own prefs file `skipti-appearance` (`theme`, `mode`, `textSize`, `haptics`, `icon`), iOS prefixes them in the shared UserDefaults (`appearance.haptics`). The parity test asserts iOS key == `"appearance." + Android key`, as the existing `haptics` pair implies.
2. **`MotionCopy` lives beside `MotionSetting` in `ThemeMotion.swift` / `ThemeMotion.kt`**, not beside `DoneCopy` in DoneMoments: `reducedNow()` must sit in ThemeMotion.swift (the spec's own guard), and Android's existing `ThemeMotionTest` already reads ThemeMotion.swift for parity, so one file pair holds the whole setting.
3. **The iOS guard is tighter than the spec's**: `accessibilityReduceMotion` may appear ONLY in Appearance.swift (once, the applier) and `isReduceMotionEnabled` ONLY in ThemeMotion.swift (once, `reducedNow`). The spec allowed both names in both files, which would have let ThemeMotion.swift's two art readers keep the phone's flag. They switch to `\.motionReduced` like every other reader.
4. **`AppearanceState.stored()` gains injectable arguments** `stored(_ defaults: UserDefaults = .standard, lowRam: Bool = MotionSetting.lowRamAtLaunch)` so the spec's "loads lessMotion from defaults" test can run without touching the host's defaults. `shared` calls it with the defaults, so nothing else changes.
5. **iOS `lowRam(totalBytes:)` takes `UInt64`** (the type of `physicalMemory`); Kotlin takes `Long`. Same rule, same vectors.
