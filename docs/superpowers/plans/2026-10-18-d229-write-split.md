# D-229 The Write Split Since D-153: Write the Id the Group Knows You By (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One account used on two phones never again writes, into a group, an id the group's other members cannot
read. New records in a group are written under the place the group knows this account by. Records already written under
the wrong id become readable on the other members' phones without rewriting them. A phone with no account behaves
exactly as today (D-153 unchanged).

**Source:** `.drafts/d227/design-review.md` (L1, L1b), `.drafts/d227/plan.md` (v1's `you_as` / `Placing`, WITHOUT its
pin), `.drafts/investigate-groups-tab/report.md` and `otherphone.mjs`. D-227 (v2, `.drafts/d227/plan-v2.md`) is merged
before this unit starts: the server already decides places from the group's own log (`creatorPlace`, `holderIn`,
`places` in `groupRoles`). Rebase on main and read D-227's merged Functions before Task 2.

**Architecture:** core computes, per group, this account's `place` (the raw member id that is its own there) and
`you_as` (the place, whenever the account's "you" is not readable to the other members there). Each shell maps the ids it
writes into a group record through one `Placing` value built from that (a REQUIRED parameter on every record builder, so
the compiler finds every writer). The creator's claim (`ownClaims`) names the place, not the merged "you", which ends the
pending-claim leak and, where no claim existed, makes the old records readable through D-158's claim alias. Phase B: a
new group op `placeAlias`, written only by a new Function `shareAliases` with the server's mark `alias: true`, tells every
phone "in this group, id y reads as place x" after the server has checked that x is the caller's place and y is the
caller's own id and nobody else's. Records are never rewritten.

**Tech Stack:** Rust core + UniFFI (bindings regenerated once), SwiftUI, Jetpack Compose, XCTest, JUnit, Cloud Functions
(plain JS, node:test against the emulators).

**Phases.** Phase A (Tasks 1A, 3A, 4A) is the forward fix and needs no cloud change. Phase B (Tasks 1B, 2, 3B, 4B) repairs
records already written; it is the founder's fork F1 in `plan-report.md`, recommended. If he declines it, drop every item
marked **[B]**; nothing in Phase A depends on Phase B.

## What the code says (verified on the tree, 2026-10-16)

1. **The symptom is not a refusal by core on the reader's phone.** `norn::Ledger::apply_expense` (`core/src/norn/mod.rs`
   ~99, `NonMemberPayer`) is called only by tests; `ffi::build_ledger` (~1290) builds no groups. On another member's
   phone a record paid by the adopted id y (not a member there, no alias for it) is stored and projected: the payer reads
   "Unknown member" (`GroupStore.label`, iOS ~297), the balance carries y as a separate person, so the creator's place x
   does not move ("balances split"), and the Who owes whom card leaves y out (`balanceNames`). A settlement from y does
   not reduce x's debt there. The plan still uses `apply_expense` / `apply_settlement` as the test ORACLE of "a member
   of this group as that phone sees it", because it is core's own membership rule.
2. **Where y gets written** (iOS; Android twins the same): `AddExpenseScreen` payer and `addedBy` = `named.selfId`
   (the merged y); shares over the kv members (merged); `SettleAll` / `SettleScreen` / `RemovalFlow` settlements from
   `selfId`; `GroupStore.setYourName` renames `me.id` in every group through `save` -> `appendGroupOps`;
   `reviseExpense` (editor, money); `RemovalFlow.records` (redistribution shares, `removeMember`); the D-166 import
   (`ImportFlow` binds the "you" column to `group.selfId`, written by `appendExpenses`).
3. **L1b confirmed by reading.** `CloudRecords.ownClaims` (iOS `CloudSync.swift` ~807, Android `CloudSync.kt` ~924)
   claims `member: you.id` when no claim names one of the account's ids and the MERGED members contain `you.id`. In a
   group made under x, the merged members contain y but the raw members do not, so core files the claim as pending
   (`groups.rs` claims pass: member not in `b.names`), it never appears in `g.claims`, and every `pushAll` appends and
   uploads another one. The fix below makes the next claim land; leaked pending claims stay harmless (they wait for a
   member nobody will add).
4. **The two real cases.** In a group G made under x before the phone adopted y:
   - (i) no claim on x yet (the phone adopted y before its first push): the fixed `ownClaims` writes `{member x, you y}`.
     That is the FIRST claim on x, so every phone (0.4.0 included, D-158) reads y as x in G: new AND old y-records become
     readable with no new trust (the same claim op every joiner writes);
   - (ii) a claim `{x, you x}` already stands (the phone was signed in and pushed before it learned y; the
     investigation's case: the phone whose "you" is older signs in second). A second claim with `you y` is contested by
     core's rule ("another account's claim"), and core cannot tell it is the same account (claims are phone-written, the
     record carries no verified author). Only the server can verify that: Phase B.
5. **A hole in D-158's claim aliases (found while reading, not reproduced).** Any member may write a claim on an unclaimed
   member U with `you` = another member's raw id D; every other phone then reads D as U in that group (`project`, the
   D-158 alias loop has no check), so Dee's existing records read as U. This unit adds a second alias source and must
   define precedence anyway, so it closes this too (Design 6).

## Design

1. **Core decides the place, per group, from the group's own records.** With `mine` = the account's "you" plus
   `other_you_ids` (final, after claims), "present" = the latest add or remove (D-186), and "claimed by another" = a
   winning claim on the member whose `you` is not in `mine`, `place` is:
   1. `you` itself, when it is a raw member, present, and not claimed by another;
   2. else the member of the first winning claim, in member order, whose `you` is in `mine` and whose member is present;
   3. else the first raw member, in member order, that is in `mine`, present, and not claimed by another;
   4. else none (and none for every group when there is no "you").
   DECIDED (controller, for the founder): computed in core, not from the server's `places`, because a phone must write
   correctly offline and with no account, and the projection is already the one source both shells read. For a creator
   it gives `members[0]` of the create, the same place D-227's server derives (residue 4 notes the one case they could
   differ).
2. **`you_as`: write as the place only when "you" is not readable.** "You" is readable in a group when rule 1 holds, or a
   winning claim there has `you == you.id` on a present member (others read it through D-158's alias). Then `you_as` is
   none and the phone writes "you" as today; otherwise `you_as = place`. DECIDED: a marked `placeAlias` (Phase B) does NOT
   count as readable, because 0.4.0 builds cannot read that op; the phone keeps writing the place, which every build
   reads.
3. **The shells map only what goes into the RECORD, never the kv ledger.** kv is the merged view (D-154: every id of the
   account reads as y). A record written with x merges back to y on the account's own phones, so kv stays as it was and
   the next rebuild produces the same bytes. Mapped: payer, shares (collapsed shares ADDED in the first one's place, by
   core), `addedBy`, a revision's `editor` and money, settlement `from` and `to`, redistribution `from` and shares,
   `renameMember.member`, `removeMember.member`. Not mapped: `create`, `addMember`, claims, personal records, the
   D-141 and D-153 backfills and the D-211 migration (they re-create what was already written; mapping them would mint
   duplicates, D-154's lesson). DECIDED: `placing:` is a REQUIRED parameter of every record builder and of
   `appendGroupOps`, with `Placing.none` written out at the backfills and the personal writers, so a writer added later
   cannot forget the decision (v1's report named a missed writer as the likeliest defect).
4. **`ownClaims` claims the place:** for a group with no winning claim whose `you` is in `mine`, and with a `place`,
   write `claim(group, member: place, you: you.id)`. It lands (the place is a raw member), so it is in `g.claims` on the
   next push: the leak ends. Case (i) groups become readable at once.
5. **[B] `placeAlias`: a server-verified alias.** New group op `{"op":"placeAlias","group":G,"member":x,"you":y}` (group
   scope). Phones build it, never store or upload it themselves; the `shareAliases` Function checks it and writes it with
   `alias: true` (firestore.rules' `validRecord` already refuses that field from a phone: its `hasOnly` list); phones
   import a `placeAlias` only with the mark, as `memberProfile` (D-211). The Function writes it only when ALL hold:
   - the caller is a member and holds place x (D-227's `holderIn` via `placeIn`, `target === uid`), x is a place in the
     log and not removed;
   - y is 32 hex, `y !== x`, y is not a place in the log (no `create` or `addMember` names it);
   - no claim op in G authored by another uid has `you === y`, and no marked alias in G names y for another place (the
     same place again is "already done", counted shared);
   - among G's CURRENT members, the caller is the ONLY account whose own personal log (`users/{u}/records`, type `3`)
     holds a `you` op with id y. A member who copies y into their own log makes it contested for everyone: a denial of
     the repair, never a takeover (they cannot get y either).
   DECIDED (controller, for the founder; the fork is whether Phase B is built at all): no data is rewritten, it fixes
   expenses, settlements, renames and redistributions alike, and nothing else can fix case (ii) without new revision
   records for every affected expense (settlements cannot be revised at all).
6. **Alias precedence and the hardening** (core): one alias per (group, from id): a marked `placeAlias` first (the
   earliest by record identity), else the first winning claim in member order with that `you`. A claim whose `you` is a
   raw member of the same group (other than the member it claims) gives NO alias; the claim itself still stands.
   DECIDED: closes finding 5 at the cost of nothing legitimate (a joiner whose own id is already a raw member keeps being
   read as that member).
7. **[B] Which ids to alias** (`AliasShare`, both shells): per group with a `place`, the account's own `you` ids that are
   not readable there (core `unaliased_yous`) AND that some record of that group actually names (raw payer, shares,
   `addedBy`, editor, settlement ends, redistribution ids, `renameMember`). DECIDED: only ids already used there, so the
   alias tells the group's members nothing they could not already infer, and no record is written for an id never used.
   Asked once per (group, id): `shared` and `skipped` answers are remembered; a transient failure is asked again at the
   next push.
8. **No account:** no register, no second phone, no adoption; `you` is a raw member of every group it made, so
   `you_as` is none everywhere and `Placing` changes nothing. The D-152/D-153 goldens stay untouched and green.
