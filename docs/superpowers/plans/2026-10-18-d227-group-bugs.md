# D-227 Two Group Bugs: Balance's New Group, and Whose Place Is Whose in a Group (Implementation Plan, v2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- (a) iOS: a group made from Balance, and a name set there, show at once on every tab.
- (b) Both shells and the Functions: one account used on two phones is recognised in each group by the place that
  group knows it by. The owner then sees the Owner pill and the owner's actions, other members see it too, and
  `shareProfile` shares. Nothing any phone writes changes.

**Source:** `.drafts/investigate-groups-tab/report.md` (repro, `otherphone.mjs`), `.drafts/d227/design-review.md`
(why v1's pin was replaced; the security analysis). v1 (`plan.md`) is superseded except Tasks 2 and 3, which are
kept as they were.

**Architecture:** the server stops using `users/{uid}.participantId` to decide who holds a place in a group. The
creator holds the first member of the first `create` op the creator's account wrote. A joiner holds the place of
their accepted invite (unchanged). Everything is read from the group's log at request time, so there is no stored
field and no backfill. `groupRoles` adds `places: { owner, admins, you }` (lists of places) beside the unchanged
`owner` / `admins` participant ids. The phones compare each row's place with those lists, and take their own row's
place from `places.you`. No core change, no bindings, no rules change.

**Tech Stack:** Cloud Functions (plain JS, node:test against the emulators), SwiftUI (iOS 17+), Jetpack Compose,
XCTest, JUnit.

## Design

1. **Creator place (server).** `creatorPlace` comes from the group's type-3 records:
   - keep only the JSON `create` ops of this group whose `authorUid === group.createdBy`;
   - take the earliest by `(createdAt, hlc.millis, hlc.counter, hlc.device)`; `createdAt` is server time, set by
     the rules;
   - the result is its `members[0].id` when that is 32 lowercase hex, else null.

   `createdBy` holds it while it is in `memberUids` and the place is not removed (`groups.removedSince`, the same
   events `logOf` reads). DECIDED: read per request, not stored. Every cloud group's first create was written by its
   creator (the rules force `authorUid`; the creator is the only member until an invite is accepted), so old groups
   need nothing. `members[0]` is the creator: core's `create_named_group` puts `self_member` first.
2. **`holderIn` / `refuseHeld` / `acceptInvite`.**
   - The own-participant-id path becomes the creator path: `own = member === creatorPlace && held ? createdBy :
     null`.
   - The invite path and the conflict rules are unchanged.
   - `acceptInvite` drops the joiner's participant-id collision check. It existed only because participant ids decided
     places.
   - `participants` / `holderOf` remain only to read a participant id as such: `person`, a request's stored `you`,
     and `makeOwner`'s answer.
   - One helper reads the log once per transaction and returns `{ place, removed, creatorPlace }`.
3. **`groupRoles`.**
   - `owner` and `admins` are unchanged (participant ids, for 0.4.0 builds).
   - New: `places: { owner: [..], admins: [..], you: [..] }`. Each is the list of places that uid holds: its creator
     place if held, plus every non-ended invite it used whose place `holderIn` resolves to it. A contested place is
     skipped, not an error. `you` is the caller's own list.
   - If the creator's create is not in the cloud yet, the lists are empty, never an error.
4. **`placeIn`'s `you` check.** `you` is accepted when it is any of:
   - the target's participant id;
   - the `you` of a claim op on that place authored by the target;
   - the place itself when the target holds it as creator.

   `holderIn` still decides the holder. DECIDED: in D-227, because it is the same root cause seen from the target's
   side, and it is about 6 lines plus 2 tests.
5. **Shell roles by place.** `RoleRules.Roles` gains `places: Places?` (`owner`, `admins`, `you`: `[String]`), and
   decoding defaults it to nil (old kv caches decode). With places known, a row is the owner or an admin when its
   `place` is in that list. Without places, today's rule applies. `unjoined` stays as today, except that a row in a
   role list is joined.
6. **The viewer's own place.** The self row's `place` is the entry in `places.you`. If there are several, it is the
   one `placeFor` picks if listed, else the first sorted. When unknown, it is `placeFor` with all of the account's ids
   (`[you] + otherYouIds`). For the viewer's own row, `requestRemoval` sends `you: null`.
7. **`ProfileSync.places`** prefers the cached `places.you` of each group (passed in, the function stays pure), else
   today's rule.
8. **Asking again.**
   - The plan's `RoleAsking`: a refresh is ok only when the call succeeded and (`places` is absent, or `places.you`
     is not empty).
   - After a push that uploaded records of a group whose cached `places.you` is empty or missing, refresh that
     group's roles. That is the same point where `ProfileShare.request` runs for `gainedGroups`.
9. **(a) iOS only**, as v1 Design 7. **Roles hardening** as v1 Design 6.
10. **Out of scope** (design-review L1, L1b, L2): the write split under an adopted "you" (v1's `you_as` without the
    pin, its own unit); the suspected `ownClaims` pending-claim leak; `inviteKnown`'s participant-id lookup.

   writes), never twice at once for one group, and keep the signature only after a successful refresh, so a not-found
   (group not yet on the server) or offline answer is asked again on the next snapshot. A small pure value
   `RoleAsking` holds this (tested), replacing the bare `roleSignatures` map.

   create-group and "Add your name" completions. Android composes only the selected tab (`AppRoot.kt` ~1009), so it
