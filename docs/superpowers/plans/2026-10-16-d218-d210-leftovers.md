# D-218 The Two D-210 Leftovers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People cards stop showing zero-net loops (core cancels directed cycles out of the pairwise view, every net
unchanged), and the cloud refuses an invite for a place a member already holds at creation (createInvite, inviteUser,
inviteKnown), with phones that say so clearly and still never offer it.

**Architecture:** Core gets one pure function, `norn::cancel_cycles`, called once in `ffi::balance_line` after D-210's
collapse block, so every pairwise view (Home's People cards through `overview`, the group page, Settle up's entries)
takes it and no shell computes anything. The cloud gets one pure decision in `groups.js` (`placeHeld`) and one reader
in `index.js` (`refuseHeld`, a read-only transaction over the members' own participant ids and the place's invites, the
same facts `holderIn` reads), called by the three invite callables before anything is written or charged. The phones
already never offer a claimed place (D-159's `invitable` filter); they gain the refusal's copy and tests.

**Tech Stack:** Rust (skipti-core), Cloud Functions (plain JS, node:test against the emulators), SwiftUI, Compose, XCTest,
JUnit.

inviteUser and inviteKnown refuse with a clear message; a refusal test in firebase/tests, a CLOUD-SECURITY row the same

## Design (decisions and reasons)

1. **"Zero-net loop" means a directed cycle in the pairwise matrix; "removing equal cycles" means cancelling each cycle
   by its smallest edge (the same amount off every edge of the loop) until no directed cycle remains.**
   DECIDED (controller, for the founder). Evidence:
   - The case the founder saw (D-210 Task 1, minors ledger): a simplified Settle-all transfer past a middle person. A
     owes B 1000, B owes C 1000; Settle all says A pays C 1000; pairwise then reads A owes B 1000, B owes C 1000, C owes
     A 1000: a loop, every net 0, and People cards showing three debts nobody has.
   - The narrower reading ("only cycles whose edges are all equal") fails a realistic Settle all: A owes B 10 and C 10,
     B and C each owe D 10; Settle all says A pays D 20; pairwise is (A,B) 10, (A,C) 10, (B,D) 10, (C,D) 10, (D,A) 20.
     Everyone is at 0, yet NO cycle has all-equal edges (D,A is 20), so that reading leaves five cards on screen.
     Cancelling by the minimum edge clears it in two rounds.
   - Cancelling a cycle by an equal amount changes no one's net (each person on the loop loses the same amount owed and
     owing), so totals, `viewer_net_minor`, the Settle all plan (`transfers`, computed from nets) and Balance are
     unchanged: "totals unchanged" holds by construction and is tested.
   - It never shows a new debt: every entry left is an entry the raw pairwise view had, in the same direction, for the
     same or a smaller amount. SPEC section 5.6's worry about simplification ("you owe Carol" when you never transacted
     with Carol) cannot arise, so this is not simplification and needs no toggle.
2. **Deterministic by ascending participant id, independent of the viewer.** A matrix can be cancelled to different
   results depending on the order cycles are taken (pinned golden G4 below). Core takes the FIRST cycle a depth-first
   search finds: start nodes in ascending participant id, each node's creditors in ascending id (the BTreeMap's key
   order), the first edge to a node still on the search path closes the cycle. Fresh search after every cancellation.
   The matrix is per group and per currency and never depends on who is looking, so A's card ("B owes you 4") always
   mirrors B's ("you owe A 4"), and both phones agree because core does it once.
   DECIDED (controller, for the founder): deterministic, not "fewest cards" (a minimum is an optimisation problem with
   its own ties; the determinism and the mirror property are what matter).
3. **Where:** `norn::cancel_cycles` is called once, in `ffi::balance_line`, for every currency's matrix, AFTER the D-210
   collapse block. Both orders keep every net, but they give different entries when a removed person sits on a loop
   (golden G6); collapsing first keeps D-210's collapse exactly as recorded and tested (a collapse never turns a matrix
   without loops into one with a loop, so on loop-free input cancellation then changes nothing and D-210's goldens stand).
   It applies to group lines and personal lines alike. `norn::pairwise` itself is unchanged (it stays the raw view its
   tests pin; `simplify_group` reads only nets). No FFI signature changes, so **no bindings regeneration and no core
   version bump** (DECIDED, controller: skipti-core's version has marked export and wire changes, D-210 and D-211; this
   is neither). If a worker finds an FFI change is needed, stop and report.
4. **"A place a member already holds"** is exactly what D-210's `holderIn` already treats as held, read from what only
   the server wrote: a CURRENT member (in `memberUids`) whose own `users/{uid}.participantId` equals the place (the
   creator's place, or any member's own), or an accepted invite for the place (`usedBy` set, no `endedAt`) whose
   `usedBy` is still in `memberUids` (`groups.joinedAs`), or two such accounts (contested; held too). A place whose
   joiner was removed (invite `endedAt`, uid out of `memberUids`) is NOT held, so re-inviting a removed person keeps
   working; an open (unused) invite does not hold a place; an outsider (not a member) whose participant id equals the
   place does not hold it.
5. **The refusal's status is `already-exists`**, message `Someone has already joined as this person.` (the same words
   acceptInvite already uses for this case). DECIDED (controller): the phones map refusals by status, never by
   message, and the existing statuses already mean something else on these paths (`failed-precondition` is "They are
   already in this group." for inviteUser/inviteKnown and "already used or expired" in `InviteCopy.failure`), so a
   distinct status is the only way the phone can say the right thing without parsing server text. `already-exists` is
   returned by none of the three callables today.
6. **Order of checks** keeps every existing refusal's status: the held check comes after the membership and target
   checks and BEFORE `charge` (a refused invite costs no daily quota) and before anything is written.
7. **"The app never offers it":** both shells already list for inviting only members who are not you and whose place has
   no claim in the projection (`invitable`, D-159; creators write their own claim, joiners theirs on joining). That is
   the phone's best knowledge; the cloud's refusal is the backstop for the window before a claim arrives (or a claim
   lost to process death). The plan adds tests pinning `invitable` on both shells (none exist) and the refusal copy;
   it adds no new callable to list held places (residue).
8. **CLOUD-SECURITY "row the same day":** DECIDED (controller, for the founder): the document's own rule is that section 2
   rows record LIVE changes ("No section 2 row until it is live"); merged-not-deployed changes get a "Pending deploy at
   0.5.0" paragraph (D-210, D-211 did this). D-218 adds its paragraph and the section 4.2 control text the same day; the
   section 2 row is written on the day 0.5.0 deploys, with D-210's and D-211's.

## Global Constraints

- **Core function:** `pub fn cancel_cycles(matrix: &mut BTreeMap<(ParticipantId, ParticipantId), i128>)` in
  `core/src/norn/mod.rs`, beside `net_opposite_pairs` and `collapse`. Precondition: every entry positive, at most one
  direction per pair (what `pairwise` and `collapse` leave); a non-positive entry is a programming error
  (`debug_assert!`), never silently cancelled. Postconditions (each tested): no directed cycle; every person's net (sum
  owed to minus sum owing) unchanged; every key present was present before, with an amount at most its old amount;
  every entry positive; result identical for identical input.
- **Algorithm (the spec the Python re-derivation implements, not the Rust):** repeat { search for a cycle: for each
  node in ascending id not yet finished, depth-first, following edges `(d, c)` in ascending `c`; reaching a node on the
  current path closes the cycle `path[k..] + back edge`; if none, stop. m = the cycle's minimum amount; subtract m from
  each of its edges; delete entries that reach 0 }. Terminates: each round deletes at least one entry.
- **Goldens** (ids: A = pid(1) < B = pid(2) < C = pid(3) < D = pid(4); amounts in minor units):
  - G1 (Settle all past a middle person): (A,B) 1000, (B,C) 1000, (C,A) 1000 -> empty.
  - G2 (two loops sharing an edge): (A,B) 10, (A,C) 10, (B,D) 10, (C,D) 10, (D,A) 20 -> empty.
  - G3 (unequal loop): (A,B) 5, (B,C) 3, (C,A) 3 -> (A,B) 2.
  - G4 (order matters; pins the ascending-id rule): (A,D) 2, (B,D) 2, (C,A) 2, (C,B) 3, (D,C) 1 -> (A,D) 1, (B,D) 2,
    (C,A) 1, (C,B) 3. (Taking cycles in descending id order gives (A,D) 2, (B,D) 1, (C,A) 2, (C,B) 2 instead.)
  - G5 (no cycle, untouched): (A,B) 4, (B,C) 7 -> unchanged.
  - L1 (balance_line end to end): group expenses: B paid 1000 with A's share 1000; C paid 1000 with B's share 1000;
    settlement A -> C 1000. Viewer A: net 0, entries []. Viewer B: net 0, entries []. Viewer C: net 0, entries [].
    (Before D-218: A saw B -1000 and C +1000.)
  - L2 (partial settle): A owes B 1000, B owes C 600 (as expenses, as L1); settlement A -> C 600. Viewer A: net -400,
    entries [B -400]. Viewer B: net +400, entries [A +400]. Viewer C: net 0, entries [].
  - G6 (collapse first, then cancel; ids 1, 3, 4, 5 as `pid(n)`, person 3 removed from the group at net 0): records
    giving the raw matrix (1,4) 1, (1,5) 3, (3,1) 1, (4,5) 3, (5,3) 1 (each edge (d, c) is an expense paid by c with
    d's share that amount). Collapse then cancel gives (1,4) 1, (1,5) 2, (4,5) 3: viewer 1 entries [pid(5) -2,
    pid(4) -1], net -3; viewer 4 [pid(5) -3, pid(1) +1], net -2; viewer 5 [pid(4) +3, pid(1) +2], net +5. (Cancel
    then collapse would give (1,5) 3, (4,5) 2.)
  - Every golden above was derived by the controller in Python from this spec; the worker re-derives them independently
    (`.drafts/d218/cycles.py`, written from the spec above, never from the Rust) and the test cites it.
- **Cloud constants (exact):** in `firebase/functions/index.js`, `const HELD = 'Someone has already joined as this
  person.';` used by the new refusal (status `already-exists`) AND by acceptInvite's existing refusal (status there
  stays `failed-precondition`). Pure decision `export function placeHeld(ownUids, invited)` in `groups.js`: true when
  `ownUids` (the CURRENT members whose own participant id is the place) is non-empty, or `invited.uid` is set, or
  `invited.contested`; false otherwise (and for malformed input: `ownUids` not an array counts as empty, `invited`
  missing counts as `{ uid: null, contested: false }`).
- **Shell copy (exact, twins):** iOS `InviteCopy.held`, Android `InviteCopy.HELD`, both
  `"Someone has already joined as this person."`. `InviteCopy.failure` maps `ALREADY_EXISTS` to it (no current caller
  of `InviteCopy.failure` can receive `ALREADY_EXISTS`: createInvite, peekInvite, acceptInvite and the D-198 phone
  callables never return it; the worker re-checks this by reading each). A new `People.inviteFailure(error)` (iOS) /
  `People.inviteFailure(error)` (Android) maps `ALREADY_EXISTS` to the held copy and everything else through
  `People.failure`; `People.failure` itself is unchanged (`ALREADY_EXISTS` there stays "That username is taken.").
- No em dashes anywhere (code, comments, copy, commits, docs). Commits end `[skip ci]`; explicit paths only;
  `git diff --cached --stat` before every commit; no attribution of any kind; never stash, reset, checkout or restore.
- **Nothing deploys.** No `firebase deploy`, no gcloud writes, no production reads; emulators only
  (`scripts/firebase-rules-test.sh`). The cloud half ships with 0.5.0.
- iOS tests: boot `AFAF4221-F35B-4CD6-8ED9-A4AFD84C6D51` first, `-collect-test-diagnostics never`, one class at a time
