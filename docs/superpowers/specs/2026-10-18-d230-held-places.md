# D-230 Held places: the server says who holds a place, and core believes only that (design)

Date 2026-10-18, session 7. Founder's call (pop-up, same day): the G-08 unit is built BEFORE 0.5.0, as approach
"A plus the join-time mark". Findings behind it: `.drafts/s7/redecide.md`.

## 1. The problem, in one paragraph

In a group, who a member IS (which account, which "you" id) is decided today by phone-written `claim` records, ordered
by a record identity the phone chooses. CLOUD-SECURITY G-08: a claim written before the victim's own claim, with a
backdated record identity or simply written before the victim joined by someone who already knew the victim's id, makes
the victim's group read-only (decision 44's denial) and, once the forger's member leaves, reads the victim's history
as the forger's member on every phone. Core cannot tell such a claim from an honest one: a record carries no verified
author, and only the server knows whose an id is (`users/{uid}.participantId`, the account's own personal log). D-229's
hardening (decisions 44, 47, 49 to 51) turned every takeover it could see into a denial; it could not remove the class.

## 2. The fix

Mirror D-229's marked alias. A new group op, **`heldPlace`** `{group, member, you}`: "in this group, place `member` is
held by the account whose id is `you`". Phones build it and never upload it; only the server writes it, with the mark
**`held: true`**, a field phones cannot write (`validRecord`'s `hasOnly`), after verifying that the caller holds the
place and owns the id. Phones import a `heldPlace` only with the mark, as they do a `placeAlias`. Core treats a marked
held place as final for its member and for its id: every unmarked claim on that member, or naming that id on another
member, is void. Unmarked claims keep today's rules among themselves, for the members no mark covers (placeholders,
members from before this deploys and the seconds between a join and its mark).

Two writers of the mark:
- **`sharePlaces`**, a new callable the phones call after a push with nothing pending (the `AliasShare` loop's twin):
  one record per (group, place, you) this phone has not seen marked; covers every existing member once.
- **`acceptInvite`**, which takes an optional built `heldPlace` record and writes it marked in the join's own
  transaction, so a new member is protected from its first second, not its first push.

## 3. The server

### 3.1 `sharePlaces` (index.js, beside `shareAliases`; pure checks in groups.js)

`groups.checkHeldRecords(records)`: 1 to 50 records, each a type-3 `heldPlace` op with exactly `op`, `group`,
`member`, `you`, three 32-hex ids (`you` MAY equal `member`: a creator's raw place), well formed (`recordShape`), no
record id twice, no (group, member) twice. Then the call is charged to a new daily quota **`places`** (100 records a
day per account, `people.LIMITS`), before anything is read. Per record, in order, the same shape as `shareAliases`:

1. The record's HLC millis is within **10 minutes** of the server's clock, else skipped (a marked record's identity
   must be an honest time: core orders marks by it, section 4.3).
2. The caller's own ids: `you` is the caller's `participantId` or a `you` op in its own log (`yousOf`, read first;
   `you === member` is accepted only when the holder below holds it as creator, since that place is the creator's own
   raw "you").
3. `you` is no OTHER account's `participantId` (decision 47's query, `limit(2)`).
4. In one transaction: the caller is a member; `holderIn(member)` resolves to the caller (contested throws `CHANGED`:
   skipped); the log made the place and it is not removed; no other current or former member's own log holds `you`
   (decision 46's set; a copy is a denial, never a takeover); no marked held place of this (group, member, you) exists
   yet (exists: already done, shared, nothing written); the record id holds no document. Then `tx.create` with
   `heldDoc` (`removalDoc` minus `removal`, plus `held: true`).

A marked held place for the same member with a DIFFERENT `you` is NOT a refusal: it is written (a two-phone account's
other id, or the creator place's new holder after decision 36's race); core takes the latest (section 4.3). Every
refusal is the same skip (`permission-denied`, "Not yours to share."); the log carries only the code. Answer
`{ shared, skipped }`.

### 3.2 `acceptInvite` with a record

`request.data.record` is optional. When present it must pass `recordShape`, be a `heldPlace` op whose `group` is the
invite's `groupId`, whose `member` is `invite.memberId` and whose `you` passes checks 1 to 3 above, and the transaction
must find no other current or former member's log holding `you` and the record id free. Then it is created marked in
the same transaction as the join. A record that fails any check does NOT fail the join: the join proceeds, the mark is
left to `sharePlaces`, the code is logged. No quota: one record per accepted invite, and invites are quota'd already.
An old build sends no record and joins as today.

### 3.3 Rules

No rules change. A refusal test in `rules.test.mjs`: a phone cannot write `held: true` (or `held: false`) into a group
log or its own log. The mark is written only through the Admin SDK.

### 3.4 Read cost

Per record: the quota document, the caller's log (once per call), one participant-id query, the group, its type-3 log,
the place's invites, the held-place query (`where('held', '==', true)`, like the alias query) and each member's log
once per call. Bounded by the quota as `shareAliases` is; recorded for the 0.5.0 audit with it.

## 4. Core (`core/src/straumr/groups.rs`, `ffi.rs`)

### 4.1 The op

`GroupOp::HeldPlace { group, member, you }`, JSON `{"op":"heldPlace",...}`, pinned bytes test; `GroupOpIn::HeldPlace
{ group_id, member_id, you_id }` across the FFI both ways; a bad one refused both ways (D-229's tests, twinned).
`make bindings` once.

### 4.2 Projection output

`ProjectedGroupOut.held: Vec<ProjectedHeld { member, you }>`, the applied marked held places in member order (one per
member, the latest), so a phone can tell which of its places are marked. Claims a held place overrides are listed in
`contested` (nothing is dropped silently).

### 4.3 Precedence (the heart of the unit)

Applied after the member set is complete, before the claims pass:
- A `heldPlace` whose `member` the group has not added waits in `pending` (as a `placeAlias` does).
- Per member: the LATEST marked held place by record identity stands (server-checked within 10 minutes, so it is
  server order in practice). The latest is also what `held_by_id` says for its `you`: one id, one member.
- A member with a held place has that as its winning claim: `claims[member] = { member, you: held.you }`, its
  `claimed_at` the held record's identity. Every unmarked claim on that member is void and reported `contested`.
- An id named by a held place: every unmarked claim naming it on ANOTHER member is void (reported `contested`), so it
  never joins decision 44's `split`, never contests a marked alias (decision 47) and never aliases; a marked
  `placeAlias` sending that id to another member is `contested` (a held place says whose the id is; an alias only
  where it reads).
- Decisions 44, 47, 49, 50, 51 then run unchanged over the claims that still count.
- `placing`: before rule 2, the member whose held place names one of `mine` is the place (present); `another(m)` is
  the held place's `you` not in `mine` when one exists, else as today. `place_lost` unchanged in form: with a held
  place of its own an account can no longer lose its place to a claim.
- `you_as` unchanged: 0.4.0 and 0.5.0 builds read only claim aliases, so "you" is readable through the account's own
  unmarked claim (which still stands, now un-contestable) or rule 1.

### 4.4 Tests (pinned, independent of the implementation)

- The G-08 pinned case flipped: the backdated claim on member 4 takes nothing once member 6 carries a held place; the
  pre-join claim (whole-branch review I2) takes nothing; a decision 44 denial is lifted by the victim's mark without
  removing anyone; the creator's raw place with a backdated foreign claim stays the creator's.
- Latest marked wins (decision 36's race: creator marked, then the invitee's mark); a held place beats a marked alias
  naming its id; a held place waits for its member; the same record again changes nothing; a held place on a removed
  member still fixes its history (the person's old records read as that member, as today's rejoin does).
- Every older golden unchanged (no "you": nothing changes; no marks: D-229's results byte for byte).

## 5. The shells (twins)

- `PlaceShare` (iOS `ProfileSync.swift`, Android `ProfileSync.kt`), `AliasShare`'s twin: `wanted(p, readOnly,
  answered)` = per group with a `place` that is not read-only, where `held` holds no `(place, you.id)`, less the keys
  answered (`place.share.answered`, "group:member:you"); records built per group with HLC stamps (`recordsByGroup`),
  calls of at most 50, the same `answer` mapping (`done`, `refused`, `later`, `RESOURCE_EXHAUSTED` later), retried at
  the next push. Runs where `AliasShare` runs (the nothing-pending branch and after a push), after it.
- `Invites.accept` (both shells) passes `record`: a built `heldPlace { group, member: invite.memberId, you: you.id }`
  when the account has a "you"; the join's answer handling is unchanged.
- Import: `refusal` takes `held: Bool`; `.heldPlace` is `.unverifiedPlace` without the mark, `.personal` in a personal
  log (`personalRefusal`); `outgoing` never uploads one (`heldType`); this phone's own marked record comes back as a
  marked alias does. `CloudRecords.ownClaims` unchanged (0.4.0 readers).
- Copy: none new. The read-only banner and "already in this group" stay as D-229 left them.
- JVM and XCTest: `wanted`, `recordsByGroup`, `answer`, the import filter (with and without the mark, personal log),
  `outgoing`, the join record (present with a "you", absent without), one round trip against the emulator in the
  existing emulator-proof lanes if cheap; sabotage every new guard once.

## 6. Records and security

- CLOUD-SECURITY: G-08 narrowed to what stays: unmarked members (placeholders, and a member in the seconds between its
  join and its mark when the join-time record failed a check), plus the one race an id can lose: `you` not yet in its
  owner's cloud log when a co-member copies it (G-31 (3), unchanged by this unit, a denial). Section 2 row on deploy
  day. New residues recorded: evicting an intruder from the creator place costs the creator path for good (decisions
  36 x 37; 0.5.1 fix `removedUid`); the lift of a decision 44 denial on an unmarked member costs that placeholder's
  place.
- BUILD-LOG D-230 row, evidence, residue, changelog; DECISIONS-TAKEN: 53 (held places, this design), 54 (10-minute
  skew), 55 (`places` quota 100), 56 (a failed join-time mark never fails the join).
- The Functions deploy order at 0.5.0 gains nothing: rules unchanged, `sharePlaces` ships with `shareAliases`.

## 7. Out of scope

Carrying `authorUid` or `createdAt` into core (not needed once the server marks); a revoke callable (the supersede
path by a later mark is the hook for one); the operator backfill (every phone marks its own places at its next push);
a mark for placeholders nobody holds (there is no account to verify).
